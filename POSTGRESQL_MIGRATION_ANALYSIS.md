# LocalAkademi PostgreSQL Migration Analysis

## 1. Executive Summary

This report analyzes the migration of LocalAkademi from SQLite to PostgreSQL. The analysis covers schema compatibility, migration history, data inventory, SQLite-specific risks, test infrastructure, Docker/CI impact, rollback strategy, and a phased implementation plan.

**Project size:** 45 Prisma models, 24 migrations, ~12,000 total rows across development database.

**Current state:** Deeply coupled to SQLite — raw SQL scripts, migration files, environment variables, test infrastructure, and backup mechanisms all use SQLite-specific constructs.

**Migration verdict: CONTROLLED DATA MIGRATION REQUIRED.** The migration history cannot be reused for PostgreSQL. A new baseline migration is required. All production data must be migrated via a custom TypeScript script.

**Key risks:**
- Case sensitivity change in `contains`/`startsWith`/`endsWith` Prisma filters
- 24 SQLite-specific migration files cannot be applied to PostgreSQL
- Backup mechanism (`VACUUM INTO`) is SQLite-only
- 45 models require verification of data type mappings

**Estimated files to change:** 50-70
**Estimated effort:** 4-6 phases, each independently verifiable

## 4. SQLite-Specific Behavior

### 4.1 Case Sensitivity (CRITICAL)

| Prisma Filter | SQLite Behavior | PostgreSQL Behavior | Impact |
|--------------|----------------|--------------------|--------|
| `{ contains: "value" }` | Case-insensitive (LIKE) | Case-sensitive (LIKE) | **Search will break** |
| `{ startsWith: "value" }` | Case-insensitive (LIKE) | Case-sensitive (LIKE) | **Search will break** |
| `{ endsWith: "value" }` | Case-insensitive (LIKE) | Case-sensitive (LIKE) | **Search will break** |
| `{ equals: "value" }` | Case-insensitive (=) | Case-sensitive (=) | **Login/auth may fail** |

**Mitigation:** Set `mode: insensitive` on affected String fields in the schema. Prisma supports this natively for PostgreSQL provider.

### 4.2 Boolean Storage

- **SQLite:** Stores Boolean as INTEGER (0/1). Prisma's `$queryRawUnsafe` returns 0 or 1.
- **PostgreSQL:** Native BOOLEAN type (true/false). Prisma maps this automatically.
- **Risk:** Any raw SQL queries referencing boolean columns as integers will break.

### 4.3 JSON Storage

| Model | Field | Storage |
|-------|-------|---------|
| BusinessProfile | `salesChannels`, `challenges` | String (JSON.stringify array) |
| UploadedDocument | `analysis` | String (JSON.stringify object) |
| TaskAssignment | `answers` | String (JSON.stringify object) |
| Multiple models | `metadata` | String (JSON.stringify object) |
| AiReviewerTelemetry | `issueCodes` | String (JSON.stringify array) |
| FormulaCalculation | `inputs`, `result` | String (JSON.stringify) |
| ActivityEvent | `detail` | String (JSON.stringify object) |

All JSON-like data is stored as TEXT/String in SQLite. In PostgreSQL, these can remain as TEXT or be migrated to native JSONB. Prisma's `Json` type maps to JSONB in PostgreSQL.

**Recommendation:** Store as TEXT during migration to minimize changes. Convert to JSONB in a follow-up optimization.

### 4.4 String Comparison

- **SQLite:** Uses BINARY collation by default but `LIKE` is case-insensitive for ASCII
- **PostgreSQL:** Uses `pg_catalog.default` collation, `LIKE` is case-sensitive
- **Risk:** `equals` filters on email, slug, and code fields are case-insensitive in SQLite but case-sensitive in PostgreSQL

### 4.5 Transaction Isolation

- **SQLite:** Serializable only (single writer)
- **PostgreSQL:** Snapshot Isolation (MVCC), configurable isolation level
- **Risk:** Lower — PostgreSQL is more concurrent-capable
- **Benefit:** No more `SQLITE_BUSY` errors

### 4.6 Foreign Key Enforcement

- **SQLite:** FK enforcement is disabled by default (`PRAGMA foreign_keys = OFF`)
- **PostgreSQL:** FK enforcement is always ON
- **Risk:** Any orphaned references that currently exist in SQLite will cause INSERT/UPDATE failures in PostgreSQL

### 4.7 AutoIncrement Behavior

- **SQLite:** `AUTOINCREMENT` guarantees IDs never reuse values from deleted rows
- **PostgreSQL:** `SERIAL`/`IDENTITY` sequences also never reuse IDs (unless manually reset)
- **Risk:** None — behavior is equivalent

1. Create new PostgreSQL container (via `docker compose --profile with-pgvector up -d`)
2. Use `prisma db push` for rapid iteration

## 9. Recommended Migration Method

**Use Method A (Prisma-based TypeScript migration script) with Option B (new PostgreSQL baseline migration).**

### Rationale

1. **Prisma handles type mapping** — No manual SQL type conversion needed
2. **Full data validation** — Each row passes Prisma's type checking on insert
3. **Idempotent by design** — Upsert by primary key
4. **Resumable** — Track progress per table/ID range
5. **Auditable** — Progress logging and verification step
6. **Minimal dependencies** — Only requires `@prisma/client` and TypeScript

### Migration Flow

```
1. prisma migrate dev --create-only    → Generate PG baseline migration
2. Apply baseline to PG                  → Create empty PG schema
3. Run migration script                  → Transfer data SQLite → PG
4. Verify row counts + checksums         → Validate integrity
5. Switch DATABASE_URL                   → Point app to PG
6. Archive SQLite database               → Keep as backup
```

5. **No delta sync needed** — migration is a one-time operation

### 13.3 Production Cutover (Future — When Real Users Exist)

1. Schedule maintenance window

## 14. Rollback Strategy

### 14.1 Pre-Migration Snapshot

Before any migration:
1. Run `scripts/backup-database.ts` to create SQLite snapshot
2. Copy entire `prisma/dev.db` to `BACKUPS/pre-pg-migration-{date}.db`
3. Verify backup integrity with `PRAGMA integrity_check`

### 14.2 Rollback During Migration

If the migration script fails:
1. **Failure mode:** Script aborts on first error
2. **State:** No data written to PostgreSQL (transactional batches)
3. **Recovery:** Fix the issue and restart the script
4. **Resume support:** Script tracks last successful table/ID

### 14.3 Rollback After Cutover

If PostgreSQL is unstable after cutover:
1. Stop the application
2. Change `DATABASE_URL` back to `file:./dev.db`
3. Restart the application with SQLite
4. Verify application works correctly
5. **Data loss:** Any data written to PostgreSQL after cutover is lost

### 14.4 Rollback Decision Criteria

| Condition | Action |
|-----------|--------|
| Migration script fails | Abort, rollback not needed (no PG data) |
| Verification fails (row count mismatch) | Investigate, re-run migration |
| Application errors after switch | Rollback to SQLite immediately |
| Performance regression >50% | Rollback to SQLite, investigate |
| Data integrity violation detected | Rollback to SQLite, fix issue |

### 14.5 Maximum Acceptable Data Loss

Since the application is not in production: **0% data loss acceptable.** Migration must be fully correct.

## 16. Findings

### DBM-001 — Prisma `contains` filter case sensitivity change

- **Severity:** Critical
- **Confidence:** High
- **Affected files:** `prisma/schema.prisma`, `src/services/knowledge.ts`, `src/services/knowledge-v2.ts`, `src/services/admin.ts`, `src/services/courses.ts`, `src/services/sources.ts`, `src/services/retrieval/lexical-knowledge-retriever.ts`
- **Evidence:** SQLite `LIKE` is case-insensitive for ASCII. PostgreSQL `LIKE` is case-sensitive. The schema has no `mode: insensitive` setting. Over 100+ uses of `contains`/`startsWith`/`endsWith` Prisma filters.
- **Risk scenario:** All text search functionality returns different results after migration. Users searching for "python" won't find "Python" content.
- **Verification:** Write a test that creates records with mixed-case titles and searches with `contains`
- **Recommended fix:** Add `mode: insensitive` to all String fields used with `contains` in Prisma schema. Enable `pg_trgm` extension. Or ensure application code normalizes case before searching.
- **Migration blocker:** No (can be fixed after migration, but UX will be degraded until fixed)

### DBM-002 — SQLite PRAGMA and VACUUM commands in scripts

- **Severity:** High
- **Confidence:** High
- **Affected files:** `scripts/backup-database.ts`, `scripts/verify-backup-restore.ts`
- **Evidence:** `VACUUM INTO` and `PRAGMA integrity_check` are SQLite-only commands.
- **Risk scenario:** Backup script crashes when `DATABASE_URL` points to PostgreSQL.
- **Recommended fix:** Rewrite backup script to use `pg_dump` for PostgreSQL and `psql` for restore verification. Add database provider detection.
- **Migration blocker:** No (backup scripts are not on critical path)

### DBM-003 — Raw SQL queries against `sqlite_master`

- **Severity:** High
- **Confidence:** High
- **Affected files:** `scripts/validate-migrations.ts`, `tests/topic-courses.test.ts`
- **Evidence:** Direct queries to SQLite system tables.
- **Risk scenario:** Migration validation script and topic-courses test fail on PostgreSQL.
- **Recommended fix:** Replace `sqlite_master` with `information_schema.tables` for PostgreSQL compatibility. Use Prisma introspection as alternative.
- **Migration blocker:** No (test-only concern)

### DBM-004 — Hardcoded file-based DATABASE_URL everywhere

- **Severity:** High
- **Confidence:** High
- **Affected files:** `.env`, `.env.example`, `vitest.config.ts`, `tests/e2e/helpers.ts`, `scripts/apply-migration-to-tests.ts`, `docker-compose.yml`, `.github/workflows/release.yml`, `docker-entrypoint.sh`
- **Evidence:** All `DATABASE_URL` values use `file:./*.db` format. No PostgreSQL connection strings exist in the codebase.
- **Risk scenario:** After provider change, all these references must be updated simultaneously. Missing any one will cause runtime failures.
- **Recommended fix:** Use environment-specific `.env` files. Set `DATABASE_URL` in CI via GitHub secrets. Use defaults in `.env.example` that work for development.
- **Migration blocker:** Yes — every database URL must change

### DBM-005 — Migration history is SQLite-only

- **Severity:** Critical
- **Confidence:** High
- **Affected files:** `prisma/migrations/` (all 24 files), `prisma/migrations/migration_lock.toml`
- **Evidence:** Every migration file contains SQLite-specific constructs. `migration_lock.toml` specifies `provider = "sqlite"`.
- **Risk scenario:** `prisma migrate deploy` will generate and apply SQLite SQL to the database. If run against PostgreSQL, it will fail with syntax errors.
- **Recommended fix:** Create new baseline migration for PostgreSQL. Archive old SQLite migrations.
- **Migration blocker:** Yes — the entire migration history must be replaced

### DBM-006 — Test fixtures use SQLite-specific `db push`

- **Severity:** Medium
- **Confidence:** Medium
- **Affected files:** `vitest.config.ts`, `scripts/apply-migration-to-tests.ts`, `tests/*.test.ts`
- **Evidence:** Test databases are SQLite files created by `prisma db push`. `vitest.config.ts` hardcodes `DATABASE_URL: 'file:./test.db'`.
- **Risk scenario:** Tests pass with SQLite but fail on PostgreSQL, creating false confidence.
- **Recommended fix:** Use PostgreSQL testcontainers for integration/E2E tests. For unit tests, keep SQLite if no database-specific behavior is tested.
- **Migration blocker:** No (can be addressed after schema migration)

### DBM-007 — `@updatedAt` timestamp precision

- **Severity:** Low
- **Confidence:** Medium
- **Affected files:** `prisma/schema.prisma` (all models with `@updatedAt`)
- **Evidence:** SQLite `DATETIME` has millisecond precision. PostgreSQL `TIMESTAMP(3)` also has millisecond precision. Prisma manages `@updatedAt` automatically.
- **Risk scenario:** None expected — precision is equivalent.
- **Recommended fix:** No change needed.
- **Migration blocker:** No

### DBM-008 — JSON fields stored as plain TEXT

- **Severity:** Medium
- **Confidence:** Medium
- **Affected files:** All models with `String @default("{}")` or `String @default("[]")` fields
- **Evidence:** JSON-like data is stored as TEXT strings. Some fields like `metadata: String` contain `JSON.stringify(...)` output.
- **Risk scenario:** Parse errors during migration if any field contains invalid JSON. Performance degradation if frequently querying JSON fields.
- **Recommended fix:** Validate JSON during migration. Consider migrating to `Json` type (→ JSONB in PostgreSQL) in a follow-up optimization.
- **Migration blocker:** No (data migration script should validate JSON)

### DBM-009 — No `DATABASE_URL` validation in application

- **Severity:** Low
- **Confidence:** High
- **Affected files:** `src/lib/prisma.ts`
- **Evidence:** PrismaClient is created without any connection validation or pool configuration.
- **Risk scenario:** Database connection failures manifest as runtime errors instead of startup errors.
- **Recommended fix:** Add connection validation at startup (similar to `validateJwtSecret()`). Configure pool settings appropriate for PostgreSQL.
- **Migration blocker:** No
